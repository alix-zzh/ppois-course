# Общие требования к лабораторным работам

Документ описывает требования, единые для всех лабораторных работ курса
«Проектирование программного обеспечения интеллектуальных систем».
Требования к конкретной лабораторной работе см. в соответствующем файле
(`lab1.md`–`lab4.md`).

## Допустимые языки программирования

Разрешено использовать один из следующих языков: **C++, Java, C#, Python**.

Часть заданий исторически сформулирована в терминах C++ (шаблоны, перегрузка
операторов, заголовочные и cpp-файлы и т. п.). При выполнении на другом языке
такие требования нужно переносить на его собственные средства:

- если в выбранном языке нет прямого аналога конструкции (например, в Java
  отсутствует перегрузка операторов), эквивалентную функциональность следует
  реализовать доступным способом — например, именованными методами
  (`add`, `equals`, `compareTo` и т. д.);
- смысл требования (инкапсуляция, разделение интерфейса и реализации,
  тестируемость) должен сохраняться независимо от языка.

Подробности по каждому заданию — см. соответствующий файл лабораторной работы.

## Требования к тестированию

- Каждая лабораторная работа должна быть покрыта unit-тестами с покрытием
  **более 90 %**.
- Тесты должны запускаться из консоли (без привязки к конкретной IDE).

## Требования к репозиторию

- Все лабораторные работы должны быть загружены в git-репозиторий.
- В репозитории не должно быть файлов, не относящихся к исходному коду
  (артефакты сборки, файлы IDE и т. п.) — используйте `.gitignore`.

## Академическая честность

- Все лабораторные работы должны быть выполнены самостоятельно и пройти
  проверку на плагиат.
- Существенным нарушением считается совпадение свыше **50 %** — в этом случае
  назначается дополнительная лабораторная работа.
- Допустимый уровень заимствований (типовые конструкции языка, шаблонный код
  и т. п.) — около **30 %**.

## Защита лабораторной работы

- Устная защита теории: **5 вопросов** из списка вопросов (см. `questions.md`).
- Письменная защита теории: **10 вопросов** из списка вопросов.

## Итоговая мини-лекция по теории

По итогам **всех** лабораторных работ (а не после каждой отдельной) нужно
записать мини-лекцию с ответами на **все** вопросы из списка (см.
`questions.md`), примерно по **1–2 минуты на вопрос**. Это отдельное
итоговое задание, сдаётся один раз в конце.

## Сборка, тестирование и CI/CD

- Проект должен собираться и тестироваться из консоли, без использования IDE.
- Необходимо настроить CI/CD-пайплайн на GitHub, который автоматически:
  - запускает тесты и проверяет покрытие кода;
  - проверяет качество кода (статический анализ / линтер);
  - собирает артефакт сборки и публикует его в разделе Releases репозитория.
- Итоговый артефакт должен быть проверяемым: его можно скачать из Releases и
  запустить независимо от среды разработки.

## Частые ошибки

При проверке работ чаще всего встречаются следующие проблемы — проверяйте
их перед сдачей:

1. **Магические числа и захардкоженные значения.** Такие значения нужно
   выносить в именованные константы или конфигурационный файл.
2. **Переусложнённый код.** Не усложняйте решение сверх необходимого —
   лишние абстракции и конструкции затрудняют чтение кода.
3. **Глубокая вложенность.** Вложенность циклов и конструкций `if-else`
   более 3 уровней в одном методе — сигнал к тому, что код нужно разбить на
   отдельные функции.
4. **Слишком большие методы.** Метод или функция длиннее ~20 строк
   (примерно одного экрана в IDE) обычно стоит разбить на более мелкие.
5. **Слишком длинные строки.** Строка кода не должна превышать ~150 символов
   (ширину рабочей области IDE).
6. **Лишние файлы в репозитории.** Не загружайте в git файлы, не относящиеся
   к исходному коду (сборочные артефакты, файлы IDE, временные файлы) —
   настройте `.gitignore`.
7. **Неинформативные имена.** Избегайте односимвольных и бессмысленных имён
   переменных, функций и классов: `temp`, `buffer`, `k`, `p`, `k1`, `k2`,
   `bcv`, `draft3`, `help` и т. п.
8. **Несогласованный стиль кода.** Придерживайтесь единого стиля именования
   и форматирования на протяжении всего проекта (не смешивайте `camelCase` и
   `snake_case`, разный регистр первой буквы и т. д.).
9. **Закомментированный и мёртвый код.** Удаляйте неиспользуемый код вместо
   того, чтобы оставлять его закомментированным; не оставляйте `TODO` в
   финальной версии.
10. **Цепочки вызовов без промежуточных переменных.** Не передавайте
    результат одной функции напрямую в другую в несколько вложенных уровней —
    это ухудшает читаемость; используйте промежуточные переменные с понятными
    именами.
